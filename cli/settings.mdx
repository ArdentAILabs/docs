Settings control what each **new branch** looks like, per connector: the database name in its URL, and SQL that runs right after it's created.

| Key | What it sets |
| --- | --- |
| `default_db` | The database name used in branch connection URLs |
| `branch_sql` | SQL that runs once on every new branch, right after creation |

## branch_sql: shape every new branch

`branch_sql` is how teams make every branch come up ready — without each developer keeping their own setup script.

Common uses:

- Redact or anonymize sensitive values on every branch.
- Add fixtures or baseline rows.
- Apply DDL your app expects in test environments.

For anonymization patterns, see [Security](/security#branch-anonymization).

<Warning>
  `branch_sql` runs on new branches, never on your source database. Keep it safe to run more than once where you can, so branch creation stays predictable.
</Warning>

## ardent settings list

```bash
ardent settings list
```

<Accordion defaultOpen={false} title="Example output">
```text
Connector: prod-db
  default_db   myapp
  branch_sql   (not set)   SQL to run on every new branch after creation
```
</Accordion>

## ardent settings set

```bash
ardent settings set default_db myapp
```

For `branch_sql`, pass SQL inline or point at a file with `@`:

```bash
ardent settings set branch_sql @./branch-init.sql
```

<Accordion defaultOpen={false} title="Advanced: run more than one branch_sql script">
Give each script a name with `--hook`, and control order and context:

```bash
ardent settings set branch_sql @./anonymize.sql --hook anonymize --order 1
ardent settings set branch_sql @./fixtures.sql  --hook fixtures  --order 2
```

| Flag | What it does |
| --- | --- |
| `--hook <name>` | Names this script, so several can exist side by side |
| `--order <n>` | Run order across scripts (lower runs first) |
| `--database <db>` | Run against this database instead of the default |
| `--run-as <role>` | Run as this role |
| `--no-database`, `--no-run-as` | Clear a previously set override |

Remove a named script with `ardent settings remove branch_sql --hook <name>`.
</Accordion>

## ardent settings remove

```bash
ardent settings remove branch_sql
```

## Local Supabase linking

If you run Supabase locally, Ardent can point its services — auth, REST, realtime, storage — at an Ardent branch instead of the local Postgres container. Useful when you want the full local stack running against isolated, real data.

### ardent settings supabase status

Is a local Supabase project linked right now?

```bash
ardent settings supabase status
```

If you have several local Supabase projects, name one with `--project <id>` (the Supabase CLI project id).

### ardent settings supabase link

Link local Supabase to the current branch:

```bash
ardent settings supabase link
```

Or to a specific branch:

```bash
ardent settings supabase link my-feature --project my-app
```

The CLI checks that local Supabase is running before it changes anything. Use `--skip-health-check` only if you've stopped the services yourself.

### ardent settings supabase unlink

Put local Supabase back on its own local database:

```bash
ardent settings supabase unlink
```

`--project <id>` and `--skip-health-check` work here too.
