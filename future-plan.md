# Future plan: make OpenAPI autogeneration work for the API docs

The goal: stop hand-writing the API reference. The backend is FastAPI, which can
emit an OpenAPI spec, and Mintlify can render that spec as reference pages with a
built-in "try it" playground. Once that pipeline exists, the docs can't drift from
the code the way they did this round — the spec is built from the routes themselves.

We checked whether we could turn this on today. We can't. This file explains why,
and exactly what has to change in mono to get there.

## Why autogen would fail today

Three problems, verified against `mono/app` on 2026-07-07:

1. **No response models.** Zero `response_model=` declarations across
   `app/routes/v1/`. Handlers return raw dicts and `JSONResponse` objects, so the
   generated spec would say "response: unknown" on every endpoint.
2. **The most important endpoint has no request model.** `POST /v1/branch/create`
   parses the raw request body by hand (`branching.py:788-796`). The generated
   spec would show it with no body schema at all.
3. **Everything ships in the spec.** No route uses `include_in_schema=False`, and
   `main.py` mounts every router into one app — Stripe webhooks, PostHog, the
   GitHub app plumbing, internal health, staff recovery, the `/v1/cli/*`
   namespace, and the internal `/v1/branch/route` proxy would all appear in a
   public reference.

Net: the autogenerated spec would be technically truthful, empty where it matters,
and full of endpoints we must not advertise. The hand-written docs are currently
better. This plan closes that gap.

## Phase 1 — Split public from internal (small, do first)

This phase pays for itself even before any models exist, because it produces a
spec snapshot we can diff in CI: a drift alarm.

- Decide the public surface. Proposed:
  - **Public:** projects CRUD; orgs member/invite/role endpoints; api-keys;
    connectors (preflight, create, get, list, update, delete, discover, selection,
    replica-identity-decisions, engine-setup, deletion-lock, quarantine);
    `POST /v1/branch/create`; `GET /v1/branches/{connector_id}`;
    `GET /v1/operations/{operation_id}`.
  - **Hidden:** `/v1/cli/*` (CLI-private), `/v1/branch/route` (internal proxy),
    `/v1/internal*`, staff routes, Stripe/PostHog/GitHub webhook routes, billing,
    system-info, `/v1/bootstrap`, `/v1/me`, `/v1/my-orgs` (dashboard session
    surface), `GET /v1/connectors/{id}/connection-details` (returns credentials),
    readiness-checks/attempts (debug), `validate-github-*`.
- Mechanism: tag every public route with `tags=["public"]` (most already carry a
  group tag from `include_router`; add the marker tag at the route level), then
  generate the spec and post-process it to keep only `public`-tagged paths.
  Alternative: `include_in_schema=False` on everything internal. The tag filter is
  less invasive — internal FastAPI docs at `/docs` keep working for the team.
- Declare the auth scheme once (`HTTPBearer`) and attach it to public routes.
  `verify_auth` runs inside handlers, so the scheme is declaration-only — that's
  fine; the spec just needs to say "bearer token" so the playground sends one.
- Commit the filtered `openapi.json` snapshot into mono, and add a CI step that
  regenerates and diffs it. A PR that changes the public surface now fails CI
  until the snapshot (and therefore the docs) is updated on purpose.

While in there: give `validate-github-repo` and `validate-github-auth` real auth
or confirm in writing that they're meant to be open. They currently call no
`verify_auth` at all.

## Phase 2 — Request and response models for the endpoints that matter

Don't model everything. Model the endpoints the docs feature, in this order:

1. **`POST /v1/branch/create`** — add a Pydantic request model
   (`connector_id`, `service_type`, `name`) to replace the hand parsing, and a
   shared `OperationHandle` response model (`operation_id`, `status`, `type`,
   `resource_id`) declared as the 202 response. Document the `X-Idempotency-Key`
   header as a `Header(...)` parameter so it lands in the spec.
2. **`GET /v1/operations/{operation_id}`** — `AsyncOperationResponse` already
   exists as a Pydantic model (`operations/models.py`). Attach it with
   `response_model=` and declare the `wait` query param's bounds (already typed).
   Add a documented example of the enriched `result` for `branch_create`.
3. **`GET /v1/branches/{connector_id}`** — define a `BranchRow` model for the
   normalized field set (`id`, `name`, `connector_id`, `service_type`, `status`,
   `branch_url`, `pooled_branch_url`, `pooled_branch_prisma_url`, `created_at`,
   `last_branch_activity`, `read_ready_at`, `write_ready_at`, `masked_ready_at`)
   with `extra="allow"` so the raw row's additional columns don't break clients.
4. **Connectors** — request models exist (`CreateConnectorRequest` etc.); the gap
   is responses. Start with `OperationHandle` on the async ones (discover,
   engine-setup, delete) and a typed core connector model with `extra="allow"`
   for the reads. The connector row is the most dynamic shape in the system; a
   loose-but-typed core is the honest version.
5. **Projects and API keys** — small, static shapes; quick wins.

Declare the shared error envelope (`{"detail": string}`) once and attach the
common error responses (401/403/404/409/422) to public routes via a shared
`responses={...}` dict, so the spec tells the truth about failures too.

## Phase 3 — Wire the spec into the docs

- Commit the filtered `openapi.json` into this docs repo (or fetch it at build
  time from a mono release artifact — committed copy is simpler to start).
- Point Mintlify at it in `docs.json` and let it generate the endpoint pages with
  the playground. Mintlify supports per-endpoint MDX stubs with an `openapi:`
  frontmatter key when we want curated ordering and prose around the generated
  reference.
- The current hand-written API pages split into two kinds:
  - **Guides stay hand-written:** the overview, the create-then-poll branch flow,
    error/retry guidance. Prose about *how to use* the API doesn't autogenerate.
  - **Reference becomes generated:** endpoint lists, request/response field
    tables. Delete our hand-maintained copies and add redirects.

## Phase 4 — Contract tests (keeps the spec honest)

The spec can drift from behavior too. Add a small pytest (or schemathesis) suite
in mono that hits the five core public endpoints against a test environment and
validates responses against the committed spec. Start tiny: branch create,
operation poll, branch list, project create, api-key create. This is what makes
"the docs can't lie" actually true end to end.

## What we deliberately keep out of the docs (unchanged by autogen)

Even with a perfect pipeline, these stay hidden on purpose: internal endpoints
(see Phase 1 list), the credentials-returning `connection-details` endpoint, and
auth trivia like "sending both a JWT and an API key returns 400." Technically
accurate, useful to no customer, and some of it invites building on surfaces we
don't want to promise.

## Open product questions

- Should branch delete be public API? Today it only exists as
  `DELETE /v1/cli/branches/{branch_id}`. CI users who adopt the raw API can
  create branches but not clean them up.
- Where is rate limiting enforced (the docs' `429` claim), if anywhere?
- What's the canonical list of API-key roles and scopes? The docs currently show
  `role_org_*` IDs and `branches:write`-style scopes that nobody has verified.
- Are the environments endpoints meant to be public? The CLI uses
  `GET /v1/environments/{id}` for BYOC allowlists.

## Sequencing

Phase 1 is a day or two of mostly mechanical work and immediately gives us the
CI drift alarm. Phase 2 is the real modeling work — a few days, endpoint by
endpoint, each one independently shippable. Phase 3 is docs-repo work we can do
the moment Phase 1's spec exists (even with empty schemas, the playground and
path list work). Phase 4 can trail. None of it blocks the current hand-written
docs, which stay the source of truth until the generated pages replace them.
